Để chắc chắn **token đó đúng là do server bạn sinh ra**, thường dùng 2 cách:

---

### 🔑 1. **Ký (Sign) token**

* Với **JWT**: khi tạo token, server dùng **secret key** hoặc **private key** để ký (`signature`).
* Khi nhận lại token, server kiểm tra chữ ký bằng **secret/public key**.
  👉 Nếu chữ ký khớp → chắc chắn token này **do server bạn sinh ra** và chưa bị sửa.

---

### 📂 2. **Lưu token ở server**

* Server tự sinh một **random token ID** và lưu vào database/Redis kèm thông tin user + thời hạn.
* Khi client gửi token, server tra trong database. Nếu khớp → hợp lệ.
  👉 Cách này an toàn nhưng tốn query đến DB.

---

### ⚖️ So sánh nhanh

* **JWT (ký bằng secret/private key):**

  * Không cần lưu DB, chỉ cần verify chữ ký.
  * Phổ biến trong hệ thống phân tán, microservices.
* **Token lưu DB:**

  * Kiểm soát chặt chẽ (có thể xoá token bất cứ lúc nào).
  * Phù hợp khi muốn chủ động quản lý phiên đăng nhập.

* **JWT**: verify chữ ký bằng secret/private key.

---

### 🔑 **Token (nói chung)**

* Chỉ là 1 “chuỗi bí mật” (random string) mà server sinh ra.
* Ví dụ: `2j3h4k5l6m7n8o9p`.
* Khi client gửi kèm token này → server tra DB/Redis xem có lưu token đó không → xác thực.
* Gọi là **opaque token** (token mờ, nhìn không biết chứa gì).

---

### 📦 **JWT (JSON Web Token)**

* Là **một loại token đặc biệt**, có cấu trúc 3 phần:

  ```
  header.payload.signature
  ```
* **Payload** chứa thông tin (user id, role, thời hạn).
* **Signature** đảm bảo token đúng do server sinh ra (xác thực bằng secret/private key).
* Server **không cần lưu trong DB** → chỉ cần verify chữ ký là biết token hợp lệ.

---

### ⚖️ So sánh nhanh

| Tiêu chí         | Token thường (opaque)       | JWT                              |
| ---------------- | --------------------------- | -------------------------------- |
| Cấu trúc         | Chuỗi random                | Chuỗi `header.payload.signature` |
| Chứa dữ liệu     | Không (chỉ ID)              | Có (id, role, exp, …)            |
| Cách xác thực    | Tra DB                      | Verify chữ ký                    |
| Thu hồi (revoke) | Dễ (xóa khỏi DB)            | Khó hơn (cần blacklist)          |
| Phù hợp          | App nhỏ, dễ quản lý session | Hệ thống phân tán, microservices |

---

👉 Tóm gọn:

* **Token thường** = tờ giấy có số, server giữ danh sách để đối chiếu.
* **JWT** = tờ giấy có sẵn chữ ký và thông tin bên trong, ai cũng đọc được nội dung nhưng chỉ server xác minh được chữ ký.

payload thường chứa cái gì 
Ok, đây là **5 loại thông tin thường có trong JWT payload** (claims) 👇

1. **`sub` (Subject / User ID)**
   → ID duy nhất của user, ví dụ `"sub": "123456"`.

2. **`name` hoặc `username`**
   → Tên hiển thị / username để client dễ dùng, ví dụ `"name": "Alice"`.

3. **`role` hoặc `scope`**
   → Quyền hạn (admin, user, editor…), ví dụ `"role": "admin"`.

4. **`iat` (Issued At)**
   → Thời điểm token được phát hành, ví dụ `"iat": 1695100000`.

5. **`exp` (Expiration Time)**
   → Thời gian hết hạn của token, ví dụ `"exp": 1695148800`.

---

### 🚀 **Fetch API**

* Là **API có sẵn trong trình duyệt** (native).
* Dùng để gửi request HTTP (GET, POST, PUT, DELETE...).
* Trả về **Promise**, phải tự parse JSON.
* Cú pháp hơi “dài dòng” nếu muốn xử lý lỗi, timeout, interceptors.

Ví dụ:

```js
fetch("https://api.example.com/users")
  .then(res => {
    if (!res.ok) throw new Error("Request failed");
    return res.json();
  })
  .then(data => console.log(data))
  .catch(err => console.error(err));
```

---

### ⚡ **Axios**

* Là **thư viện bên ngoài** (cài thêm qua npm/yarn).
* Cung cấp API dễ dùng hơn, có nhiều tiện ích:

  * Tự động parse JSON.
  * Hỗ trợ **timeout**, **cancel request** dễ dàng.
  * Có **interceptors** (chèn token, log, xử lý lỗi trước/sau request).
  * Tương thích tốt với Node.js (fetch chủ yếu chạy trên browser).

Ví dụ:

```js
import axios from "axios";

axios.get("https://api.example.com/users")
  .then(res => console.log(res.data))
  .catch(err => console.error(err));
```

---

### ⚖️ **So sánh nhanh**

| Tiêu chí        | Fetch (built-in)                 | Axios (thư viện ngoài)          |
| --------------- | -------------------------------- | ------------------------------- |
| Có sẵn          | ✅ Có trong trình duyệt           | ❌ Phải cài thêm (`npm i axios`) |
| Trả về          | Response object (phải `.json()`) | Data đã parse sẵn               |
| Timeout         | ❌ Không hỗ trợ trực tiếp         | ✅ Có hỗ trợ                     |
| Interceptors    | ❌ Không có                       | ✅ Có                            |
| Node.js support | Hạn chế                          | Tốt                             |
| Code ngắn gọn   | Bình thường                      | Gọn hơn, dễ quản lý             |

---

👉 Tóm gọn:

* **Fetch**: nhẹ, không cần cài thêm, đủ cho các request đơn giản.
* **Axios**: mạnh mẽ, nhiều tiện ích, phù hợp khi làm project thực tế lớn.

hướng giải quyết upload phim nặng khoảng 2gb cho fe và be thì giải quyết thế nào
Câu hỏi này thực tế đấy 👍. Upload file **nặng \~2GB** thì không thể làm kiểu “upload nguyên file một phát” vì dễ **timeout, mất mạng, tốn RAM**. FE và BE cần phối hợp theo hướng **chunk upload (chia nhỏ file)** + **resumable upload (có thể tiếp tục khi bị gián đoạn)**.

---

## 🚀 Hướng giải quyết tổng thể

### 🖥️ **Front-end (FE)**

1. **Chia nhỏ file (chunking)**

   * Dùng `Blob.slice()` hoặc `FileReader` trong JS để chia file thành nhiều chunk (ví dụ 5MB, 10MB mỗi chunk).
   * Tạo `fileId` (hash hoặc UUID) để server biết các chunk thuộc cùng 1 file.

2. **Upload tuần tự hoặc song song**

   * Gửi từng chunk qua API (`/upload-chunk`).
   * Có thể upload song song vài chunk để tăng tốc.

3. **Retry khi lỗi**

   * Nếu chunk nào fail → retry lại chunk đó, không phải gửi lại cả file.

4. **Thông báo tiến trình**

   * FE cộng dồn dung lượng chunk đã upload để hiển thị progress bar (%).

---

### 🖥️ **Back-end (BE)**

1. **API nhận chunk**

   * Nhận dữ liệu chunk + thông tin `fileId`, `chunkIndex`.
   * Lưu tạm vào disk (ví dụ thư mục `/tmp/uploads/fileId/`).

2. **Ghép file**

   * Khi BE nhận chunk cuối cùng → tiến hành merge các chunk thành 1 file lớn.

3. **Resumable upload**

   * BE nên hỗ trợ query “file này đã có chunk nào rồi” để client chỉ upload phần còn thiếu (tránh upload lại từ đầu khi mất mạng).

4. **Giới hạn & bảo mật**

   * Giới hạn dung lượng tối đa (vd 2GB).
   * Xác thực người upload (JWT, session).
   * Clean up chunk tạm sau X giờ nếu upload không hoàn tất.

---

## ⚖️ Một số công nghệ hỗ trợ

* **FE**:

  * [tus.io](https://tus.io/) (protocol cho resumable upload).
  * [uppy.io](https://uppy.io/) (JS lib hỗ trợ chunk upload).
* **BE**:

  * Node.js: dùng `multer`, `busboy`, hoặc `formidable`.
  * Python: dùng `FastAPI`/`Django` xử lý stream upload.
  * Có thể dùng **S3 / Cloud Storage** hỗ trợ multi-part upload (AWS S3, GCP, Cloudflare R2).

---

## 🎯 Tóm gọn

* **FE**: chia file thành chunk nhỏ + upload tuần tự/song song + retry khi fail.
* **BE**: lưu chunk + merge lại thành file hoàn chỉnh + hỗ trợ resume.
* Nếu dùng cloud (AWS S3, GCP) → nên tận dụng **multi-part upload API** (họ làm sẵn, rất tối ưu).

kỹ thuật streaming 
À, bạn nhắc đến **streaming** thì nó khác với “upload nguyên file rồi mới xem” nhé 👍.

---

## 🔑 Ý tưởng chính của **Streaming**

* **Không tải toàn bộ file trước**, mà **chia nhỏ file thành nhiều đoạn (chunk)** và truyền dần khi người dùng xem.
* Người xem **xem được ngay** trong khi dữ liệu còn đang tải.
* Giảm tải băng thông và cải thiện trải nghiệm.

---

## 🎥 Các kỹ thuật streaming phổ biến

### 1. **Progressive Download** (giả streaming)

* File video để trên server (ví dụ `.mp4`).
* Trình duyệt/media player dùng **HTTP Range Requests** để tải từng đoạn.
* Người dùng có thể tua (seek) đến giữa video → chỉ tải phần đó.
  👉 Đơn giản, dễ triển khai (ngay cả Nginx/Apache cũng hỗ trợ).

---

### 2. **HLS (HTTP Live Streaming – Apple)**

* Server **cắt video thành nhiều đoạn nhỏ** (chunk `.ts`, thường 2–10 giây).
* Tạo file playlist `.m3u8` để client biết thứ tự và chất lượng.
* Client (browser, app) phát từng chunk → có thể chuyển chất lượng (adaptive bitrate).
  👉 Chuẩn phổ biến nhất, hỗ trợ iOS, Android, web.

---

### 3. **MPEG-DASH (Dynamic Adaptive Streaming over HTTP)**

* Giống HLS nhưng là chuẩn mở, không phụ thuộc Apple.
* Dùng file manifest `.mpd` thay cho `.m3u8`.
* Adaptive bitrate streaming: tuỳ băng thông mà chuyển chất lượng (360p ↔ 1080p).

---

### 4. **RTMP (Real-Time Messaging Protocol)**

* Giao thức cũ (Adobe/Flash), hiện ít dùng cho client nhưng vẫn phổ biến để **ingest video** vào server (ví dụ từ OBS → YouTube).
* Thường kết hợp với media server (Nginx-RTMP, Wowza).

---

## ⚙️ Triển khai streaming thực tế

* **Frontend (FE)**:

  * HTML5 `<video>` tag hỗ trợ HLS (Safari) hoặc dùng lib như [hls.js](https://github.com/video-dev/hls.js) để phát `.m3u8` trên mọi trình duyệt.
  * MPEG-DASH thì có [dash.js](https://github.com/Dash-Industry-Forum/dash.js).

* **Backend (BE)**:

  * Chuẩn bị video bằng FFmpeg: cắt chunk + tạo playlist.
  * Host trên CDN hoặc server (Nginx, Node.js).
  * Nếu live streaming: dùng Nginx-RTMP hoặc Media Server để chuyển thành HLS/DASH.

---

## 🎯 Tóm gọn

* **Upload 2GB** → dùng **chunk upload** để đưa video lên server an toàn.
* **Phát video 2GB** → dùng **streaming (HLS/DASH)** để người dùng không cần tải hết mới xem, lại có thể tua và đổi chất lượng.

**Streaming video** trong IT là kỹ thuật **không tải toàn bộ file video về một lần**, mà **chia nhỏ thành nhiều đoạn** (chunk) và phát dần theo thời gian.

### Cách hoạt động:

1. Video (2GB chẳng hạn) được chia nhỏ thành nhiều đoạn (ví dụ mỗi đoạn 2–10 giây).
2. Khi người dùng mở video → chỉ tải **đoạn đầu tiên** về và bắt đầu phát ngay.
3. Trong lúc xem, các đoạn tiếp theo được tải dần về (hoặc buffer sẵn).
4. Người xem có thể tua (seek) đến một đoạn khác → server chỉ gửi đúng đoạn tương ứng thay vì toàn bộ file.

### Lợi ích:

* Người dùng xem ngay mà không cần chờ tải xong toàn bộ.
* Giảm áp lực băng thông (chỉ gửi phần cần xem).
* Hỗ trợ video dài/nặng (1–10GB vẫn xem được).

### Công nghệ phổ biến:

* **HLS (HTTP Live Streaming – Apple)**
* **MPEG-DASH (Dynamic Adaptive Streaming over HTTP – Google)**
* Kết hợp CDN để phân phối nhanh hơn.

## 🧰 Backend: Nằm ở đâu & dùng ngôn ngữ gì?

Streaming về mặt kỹ thuật là phần **backend / server-side** — vì:

* Server phải chuẩn bị video (encode / transcode) thành nhiều chất lượng, nhiều đoạn (segments).
* Phải phục vụ các HTTP Range Requests, playlist manifest (.m3u8 / .mpd), endpoint gửi segment, metadata.
* Quản lý CDN, cân bằng tải, bảo mật, xác thực, rate limit, caching…

### Ngôn ngữ & công nghệ thường dùng:

| Thành phần                                                    | Ngôn ngữ / công nghệ thường dùng                   | Ví dụ / ưu điểm                                                                                                                                                                                                                 |
| ------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| *Xử lý video / encode / transcode*                            | **FFmpeg** (tool, C/C++), **GStreamer**, **Libav** | Phổ biến để chuyển video sang các định dạng, cắt segment, tạo bitrate khác nhau                                                                                                                                                 |
| *Server streaming HTTP (Range / static segments / playlists)* | Node.js, Go, Python, Java, C++                     | Triển khai endpoint để phục vụ segment, manifest; Go thường được dùng vì hiệu suất tốt khi xử file lớn và stream byte ranges. Ví dụ bài viết “Video Streaming with Go” minh họa cách server đáp Range header. ([Dev Genius][2]) |
| *Media server chuyên dụng / giải pháp open source*            | C++, Java                                          | Ví dụ: **OvenMediaEngine** viết bằng C++, chuyên low‐latency streaming. ([Wikipedia][3]); **Red5** viết bằng Java. ([Wikipedia][4])                                                                                             |
| *CDN / phân phối nội dung*                                    | —                                                  | Khi có lượng người xem lớn, dùng CDN để cache segment, giảm độ trễ, tải server                                                                                                                                                  |

## 1️⃣ YouTube dùng streaming kiểu nào?

### a) **Adaptive Bitrate Streaming (ABR)**

* Khi bạn xem video, YouTube không gửi một video nguyên file.
* Nó **chia video thành nhiều đoạn nhỏ (chunk, segment)**, mỗi đoạn có nhiều chất lượng (360p, 720p, 1080p…).
* Player tự động chọn **chất lượng phù hợp với tốc độ mạng** → tránh giật lag.
* Chuẩn mà YouTube dùng tương tự **MPEG-DASH** cho web và **HLS** cho iOS.

### b) **Chunk + Manifest**

* Video được encode thành nhiều **bitrate**.
* Tạo file **manifest** (MPEG-DASH `.mpd`) chứa danh sách các segment và chất lượng.
* Khi client request: YouTube gửi từng segment → FE ghép phát liên tục.

---

## 2️⃣ Cách YouTube xử lý streaming

1. **Upload video**

   * FE upload file (có thể chunk upload cho video nặng).

2. **Transcode / Encode**

   * Server convert video sang nhiều **bitrate & resolution**.
   * Tạo **segments** (2–10 giây) + manifest (playlist).

3. **Phát video**

   * Browser / app lấy **manifest**.
   * Tải từng segment → phát liên tục.
   * Player auto switch chất lượng theo network → ABR.

4. **CDN & Cache**

   * Các segment được lưu trên **CDN** toàn cầu → người xem gần node nào sẽ lấy từ đó → giảm latency.

---

## 3️⃣ Tóm gọn

| Bước     | YouTube làm gì                               |
| -------- | -------------------------------------------- |
| Upload   | Chunk upload, lưu tạm, validate              |
| Encode   | FFmpeg / Media server tạo nhiều bitrate      |
| Segment  | Cắt video ra 2–10 giây mỗi segment           |
| Manifest | MPEG-DASH `.mpd` / HLS `.m3u8`               |
| Delivery | Client fetch từng segment + adaptive bitrate |
| CDN      | Cache segment toàn cầu, giảm tải server      |

Ok, mình tóm gọn các bước để triển khai **video streaming** (dùng cho CNTT / web app) theo flow thực tế, dễ hiểu:

---

## **Bước 1: Upload video**

* **FE (Front-end)**:

  * Chia file lớn thành **chunk nhỏ** (vd 5–10MB).
  * Upload từng chunk → tránh timeout và mất dữ liệu nếu mạng yếu.

* **BE (Backend, Django/Node.js/Go)**:

  * Nhận chunk → lưu tạm.
  * Hỗ trợ **resume upload** (tiếp tục upload khi bị gián đoạn).

---

## **Bước 2: Encode / Transcode video**

* **Dùng FFmpeg** để:

  * Chuyển video sang **nhiều định dạng & bitrate** (360p, 720p, 1080p).
  * Tạo các **segment nhỏ** (2–10 giây) để client fetch dần.
  * Tạo **manifest / playlist**:

    * HLS: `.m3u8`
    * DASH: `.mpd`

> Ví dụ FFmpeg:

```bash
ffmpeg -i input.mp4 -codec: copy -start_number 0 -hls_time 5 \
-hls_list_size 0 -f hls index.m3u8
```

---

## **Bước 3: Lưu trữ / phân phối**

* **Static segments + playlist**:

  * Lưu trên server hoặc storage (AWS S3, GCP Storage).
* **CDN**:

  * Cache segment toàn cầu → giảm độ trễ, tăng tốc độ tải video.

---

## **Bước 4: Backend phục vụ streaming**

* Server cung cấp **endpoint**:

  * `/video/playlist.m3u8` → trả playlist.
  * `/video/segment0.ts` → trả segment khi client yêu cầu.
* **Django / Node.js / Go** đều có thể làm:

  * Django: `StreamingHttpResponse` hoặc serve static segment.
  * Node.js: stream file chunk theo `Range` header.

---

## **Bước 5: Front-end phát video**

* HTML5 `<video>` tag:

  * `<video src="playlist.m3u8" controls></video>`

* Dùng JS lib:

  * **hls.js** (HLS trên tất cả trình duyệt)
  * **dash.js** (MPEG-DASH)

* Player tự **fetch segment → phát → chuyển bitrate khi cần**.

---

## **Bước 6: Tối ưu nâng cao**

* Adaptive Bitrate (ABR): chọn chất lượng phù hợp tốc độ mạng.
* Cache segment trên CDN.
* Giới hạn rate, xác thực người dùng.
* Cleanup segment tạm thời sau khi upload hoặc sau 1 thời gian.

---

### ✅ **Tóm gọn flow:**

**Upload (chunk) → Backend lưu tạm → FFmpeg encode → Segment + Playlist → Lưu server/CDN → Frontend fetch + play segment**
